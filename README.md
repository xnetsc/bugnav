# bugnav — T80s 防卡困外置导航

[English](README.en.md) | 中文

给科沃斯 T80s（DEEBOT T80S 上下水版）加一个外置“大脑”：机器人本体零
改动，程序跑在一台常开宿主机上，以用户账号按官方 App 协议经科沃斯云
（deebot-client）读位置/状态/电量、发命令。三层结构：

- **控制层（确定性，每 2.5 秒样本实时生效）**：防卡困——检测卡困
  前兆与楔死，原地暂停处理或后退脱困，全程不重置原生清扫会话
  （唯一的例外是楔死脱困，见下）；
- **判断层（LLM 整场监督）**：代码只负责测量与算术
  （速度、面积、电量、充电曲线、预计完成时间），“合理不合理、继续还
  是收尾、充到多少”一律由大模型结合判断逻辑给结论，不写死阈值规则；
- **充电规划（确定性求解器）**：在“一口气扫完”与“分多轮充电”之间
  按总时间算平衡点，供判断层复核、覆盖或否决。

总目标：**清扫 + 充电 + 回站开销的总耗时最短**——早上 7 点的任务不许
拖到晚上 8 点还在扫。

**完整方案（硬件选型→软件设计→部署安装→操作流程→验证清单→运维回滚）
见 [方案.md](方案.md)。**

## 控制层：防卡困

设计前提是这台固件的实测行为：任何外部定向移动（遥控步进、
mapPoint 定点）都会丢弃正在进行的原生清扫会话，新会话重新规
划全屋、重扫已扫区域；旋转步进则被固件直接拒绝。保得住会话
（及其断点）的只有原地暂停/恢复，和机器人自己的回站 + 桩上
断点续扫。控制层因此只用这两类手段处理还能动的机器人；唯一
例外是楔死——楔死的会话本来就一平方米也扫不了，才动用步进
后退脱困。

- **挣扎前兆检测**：原固件会一直往障碍物上爬、爬到驱动轮悬空报错才
  停。本层抓前兆——清扫中小范围内反复进退、路径很长而净位移≈0、
  朝向多次反转，即判定正在硬爬，提前干预，不等错误码。
- **暂停处理**：挣扎、正面猛冲、绕圈徘徊三类前兆（机器人还能动、
  会话还在产出）统一这样处理：原地暂停、停稳片刻、恢复同一个
  会话继续扫；恢复后用一对未闩锁的检测器盯梢，同一签名再次出
  现就再暂停一次。每个位置每场有次数预算（默认 3 次），用完仍
  不行：发通知说明，并把该位置留给原生清扫、本场不再干预。这
  条路径不发出任何会重置会话的命令。
- **楔死脱困**：鼻子顶进障碍、死命往前推是另一种卡法——报错持续且
  原地不动（同一驱动轮故障会以「错误状态」或「暂停带错误码」两种
  形态出现），或清扫中位置长时间冻结、纹丝不动。这类先脱困：
  用遥控 jog 命令逐步后退（约 0.35 m/步），往前正是它楔住的原因。
  步进必然终结楔死中的会话，退出后故障清除即在原地新开全屋清
  扫。后退本身被堵住（后方有东西、步数用尽仍无位移）、或退出
  后故障仍在：判定无自力出路，停机并报警——通知发到手机/Mac
  的同时，**机器人本体连响 3 声内置提示音**，家里有人不用看手
  机也能听见；在人明显干预（被搬动或已回桩）之前不再自行动作。
- **绕圈/徘徊检测**：短窗口内困在小盘子里打转（路径长、累计转向大、
  净位移小）第一次出现即触发暂停处理，不等挣扎成形。但干预前先
  按地图确认：该点位于历史上扫过的区域边沿（其周边一整段从未被
  清扫）即判为墙壁/墙角——直边没有内部可处理，不作干预，原生沿
  边继续；碰撞点周围历史上扫过的，肯定不是墙。参照系是「曾经扫过」的全
  部格子（独立持久化、随清扫实时更新），不是监督层那份保守的全
  屋面积基线；且按地图绑定——每张地图一份自己的历史，换场地即
  换地图，坐标不可跨图套用，切换时自动换用新图的历史并通知。
- **记忆分层**：处理成功的位置短时静默（默认 15 分钟，机器人会
  在同一组家具周边继续扫，软签名可能良性复现）；次数用完的位
  置本场静默。两者都只是「不干预」，机器人照常清扫，不存在禁
  区。椅子这类移动障碍下次未必还在，绝不固化成永久禁令；跨次
  只留网格统计（哪里常卡、处理成功/放弃各多少次），不留禁令。
- **错误码响应**：105 被困、102/204 驱动轮悬空等错误码进监督视野
  并计数；持续报错且原地不动的由控制层按楔死处理（见上，后退脱困
  打头），不只记录。

## 适配层：连真机

- deebot-client 不认识本机硬件类（nazy54），运行时别名到同代 V2 能
  力集；固件 1.61.0 拒绝 `getCleanInfo`（20003），工作状态改走
  `getWorkState`（按钉住的 deebot-client 版本规范在本地补了该命令
  并注册进消息分发表），别名能力集相应打补丁。
- 订阅：位置/朝向、工作状态 + 基站状态、电量、喷水量档位 + 拖布在
  位、错误流。命令：暂停/停止/继续、回站充电、新开全屋清扫、
  mapPoint 定点移动、move 遥控步进。
- 账号凭据只经进程/容器环境变量注入，绝不写入代码与配置文件；
  device_id 固定，避免频繁重登触发设备验证。

## 判断层：LLM 监督

### 监督（整场）

按节奏复核（清扫约 20 分钟一评、回站充电必评、异常加密），裁决词
表有界：`continue / notify / abandon_current / stop_session /
ask_user`，外加可选的续扫电量覆盖与充电参数矫正（见下）。裁决
即执行；`stop_session` = 停机 + 回站，不把机器人撂在原地。

### 它拿到的测量（代码算、人不下结论）

- **滚动仪表**：最近约 15 分钟的耗电率（%/㎡）、推进速度（㎡/分）、
  新增面积；整场平均作后备。
- **预计完成时间**：剩余面积 ÷ 当前推进速度 + 电量短缺推出的充电
  轮次（每轮按充电曲线 + 回站开销计价），给出预计完成时刻、剩余总
  分钟与**整场总跨度**（已花 + 等待 + 剩余）。
- **虚拟水量表**：本机无水位传感器——按“真回站洗拖（基站连续停留
  达阈值）即补满 100%，其后按喷水档位 × 拖过面积递减”记账。
- **分段台账**：每一轮“离站→回站”单独记账（时长/面积/出发电量/
  到站电量/是否充完电出发），短周期充电抖动（充完回来没多久又没
  电、反复多轮）由此可诊断：出发电量低 = 充太少，出发高却很快见
  底 = 耗电异常。
- **推进塌陷标记**：滚动窗口内几乎零新增覆盖却一直在“清扫”——
  与总面积无关，任何场景（含陌生户型）都成立。

### 它的判断逻辑（写在提示里，是裁量依据不是死规则）

- **时长合理性按面积推导**：以合理速度扫完计划面积本应花的总时间
  为预期，实际+预计总跨度与它的比率判**效率**；不用“几小时”一刀
  切。大户型扫得久、比率相称，就是正常。
- **环境复杂度计价**：预期分乐观/保守两档——保守档按这个环境已证
  明的实际推进速度算（该速度天然含绕障成本）。障碍占住、永远扫不
  到的面积先从计划面积里扣除（可扫面积），覆盖率、剩余、预计时
  间都对可扫面积算。绕障试探的时间单独计量（“低产出时间占比”）：
  试探期间推进≈0 是合理的，不拿剔除试探后的速度要求整体。
- **总跨度底线优先于比率**：不管什么速度、比率多正常，总清扫时
  间不许被充电等待撑到不可接受（跨大半天、顶进深夜）——复杂度可
  以解释速度慢，解释不了无限长。真因环境太复杂扫不完，必须发通
  知说清：预计几点完、慢在哪里、打算怎么处置，不许无声地无限扫
  下去，也不许无声地放弃。
- **充电是平衡题**：一端是“一口气扫完剩余”（需要的出发电量按耗
  电估算 + 安全系数算出，称保证数——只是价格标签，不是必须达到
  的下限），另一端是分多轮（每轮多付一遍回站开销）。候选电量逐
  个标价：还要等多少分钟、几点能出发、能换多少面积。剩余少时一
  口气通常划算，剩余多时死等一口气反而撑爆总跨度。唯一的底线：
  别碎成短周期抖动那种碎法。
- **不必全覆盖**：覆盖率对可扫面积看；已扫很久、主体已扫完时，
  零头不值得再充一轮电去追，收尾就是合理选择。已投入时长是沉没
  成本，不构成继续的理由。
- **作息**：结合当前时刻与普通人生活习惯判断续扫是否合理；上午
  的任务拖到下午四五点还在续扫是强收尾信号（除非比率证明面积
  本就该扫这么久）。

### 充电参数：AI 按原始历史持续矫正

充电是非线性的（低电量段快、高电量段慢，如 30%→50% 可能 10 分
钟、50%→80% 可能 30 分钟），且真实曲线会漂移。代码只做原始记
录：每次回站充电存一条轨迹（起始电量、时长、电量每 +2% 的打
点），长期保存并随复核摘要发给监督模型；模型对照实测与在用参
数（分段速率表、单位面积耗电），对不上时在裁决里给出矫正后的
参数，系统校验形状后采用并持久化。代码不预设任何校正公式。

### 地图缓存一致性

全屋面积基准只来自“已采用”的历史布局：本场足迹与基准不吻合
（新格占比过高——换了地图、换了房间、带去别人家）时，判定基准
可疑，摘要**扣下**剩余/覆盖率/预计完成等派生数字（只给原始推
进与时长），避免拿错分母下错结论；不吻合的布局先存为候选，连
续两场吻合才采用为新基准，一次异地清扫不会污染基准。进度百分
比只在基准成熟后才有意义。

### 问用户（ask_user）

继续与收尾各有道理时，监督可把决定交给用户：暂停机器人（在桩
则保持停靠），发通知写清现状与选择；用户 5 分钟内按机身键或在
App 里恢复清扫 = 继续，让它回站 = 结束；**5 分钟无任何反馈 =
自动回站结束**（机身无按键事件上报，按键/App 操作以状态变化识
别，都是用户本人的选择）。

### 本户档案

可在配置里写本户清扫范围（如只扫客厅/餐厅/厨房/书房、不扫卧
室）与正常时长经验值：范围信息照用，时长与面积推导冲突时以面
积推导为准。

## 通知

监督的通知（notify 裁决、异常收尾、ask_user 提问、缓存基准变更
等）统一以 `NOTIFY` 行写入 `data/events.jsonl`，并可经 webhook
转发。Mac 宿主附带通知桥（`deploy/mac/`）：盯 events 文件 →
macOS 通知中心 + 给用户本人发 iMessage（手机同步收到），launchd
登录自启、断点续传不重放不漏发。

## 部署

- 镜像：GHCR 预构建（`ghcr.io/xnetsc/bugnav`），宿主机只拉镜像跑
  容器，只放配置类小文件，代码不落宿主机。Mac + Docker Desktop
  为当前形态；也提供 systemd 安装脚本。
- 配置：`config.json`（账号短 ID、控制/监督参数、本户档案）+
  `.env`（科沃斯账号密码、LLM 的 key/端点/模型名——OpenAI 兼容接
  口即可，已验证通义千问 qwen-plus）。全部敏感信息只在 `.env`。
- 数据（`data/`）：`samples.jsonl`（样本流，含每样本进度）、
  `events.jsonl`（事件与通知）、`home_cells.json`（全屋基准）、
  `home_candidate.json`（候选布局）、`charge_model.json`（充电参
  数，含 AI 矫正结果）、`charge_history.json`（原始充电轨迹）、
  `stats.json`（跨次卡困统计）。
- 守护进程下达的每条命令都真实执行。定点移动走 clean_V2 的
  `mapPoint`（本固件唯一实现的定向移动命令，适配层实现，控制
  层不使用——它会丢弃当前会话）；矩形区域命令
  customArea 本固件拒绝（20011），不用。

快速开始：

```bash
# 1) 先跑测试（不需要真机、不需要账号；含模拟器端到端用例）
python3 -m unittest discover -s tests

# 2) 部署到宿主机
cp config.example.json config.json   # 填科沃斯账号短 ID
sudo bash deploy/install.sh          # 或用 docker compose up -d
```

目录：`bugnav/`（核心逻辑+模拟器+真机适配）、`deploy/`（systemd 与
Mac 部署件）、`tests/`（单元测试与模拟器端到端测试）、`Dockerfile`、
`docker-compose.yml`。
